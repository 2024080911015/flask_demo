# 私聊功能修改说明

## 1. 修改背景

原系统设有一项"破冰留言"功能：用户可以在查看他人名片时发送一条文本消息，但**每对用户之间只能发送一条**。这是通过 `messages` 表的 `UNIQUE(sender_id, receiver_id)` 约束实现的。

实际使用中发现该限制过于严格——用户之间应有持续对话的能力。本次修改将"破冰留言"升级为**不限次数的私聊**，同时新增会话列表和聊天窗口界面。

## 2. 功能目标

- 移除"一对用户只能发一条消息"的限制，改为不限次数私聊。
- 消息内容限定为文本（最多 500 字），不涉及图片、文件等。
- 收件箱从"单条消息列表"改为"会话列表"，按对话伙伴分组展示。
- 新增聊天窗口：点击会话后展示完整对话记录，支持连续发送。
- 聊天窗口每 5 秒自动轮询对方新消息。
- 已有旧数据平滑迁移，不丢失历史消息。

## 3. 数据库变更

### 3.1 模型层

**文件**：`models.py`

移除了 `Message` 模型的 `UniqueConstraint`：

```python
# 旧：__table_args__ = (db.UniqueConstraint('sender_id', 'receiver_id', name='uq_sender_receiver'),)
# 新：无表级约束
```

### 3.2 数据迁移

**文件**：`app.py`（应用启动时自动执行）

由于 SQLite 不支持 `ALTER TABLE DROP CONSTRAINT`，迁移采用"建新表 → 导数据 → 删旧表 → 重命名"策略：

```text
1. DROP TABLE IF EXISTS messages_new      -- 清理残留
2. CREATE TABLE messages_new (...)        -- 不含 UNIQUE 约束
3. INSERT INTO messages_new SELECT ...    -- 迁移旧数据
4. DROP TABLE messages                    -- 删除旧表
5. ALTER TABLE messages_new RENAME TO messages
6. CREATE INDEX IF NOT EXISTS ...         -- 重建索引
```

检测条件为 `inspector.get_unique_constraints('messages')` 中是否存在 `uq_sender_receiver`。迁移仅在首次启动且检测到旧约束时执行一次。

## 4. 后端接口变更

### 4.1 发送消息（修改）

```text
POST /api/message/send
```

**旧行为**：
- 检查 `sender_id + receiver_id` 是否已有记录
- 若已有记录，返回 403 "你已经给该用户留过言了"
- 捕获 `UNIQUE` 异常并返回同样错误

**新行为**：
- 不再检查是否已发过消息
- 每次调用创建一条新消息记录
- 返回新消息的 `id`、`content`、`created_at`
- 发送成功后输入框清空，可继续发送下一条

### 4.2 会话列表（重写）

```text
GET /api/message/inbox
```

**旧行为**：返回当前用户收到的所有消息（单条维度）。

**新行为**：查询所有与当前用户相关的消息（发送 + 接收），按对话伙伴分组，返回会话列表：

```json
{
  "status": "success",
  "data": [
    {
      "partner_id": 1019,
      "partner_name": "张三",
      "avatar": "/api/user/avatar/1019",
      "last_message": "最近一条消息内容...",
      "last_time": "2026-05-30 13:00",
      "unread_count": 3
    }
  ]
}
```

按 `last_time` 倒序排列。

### 4.3 对话详情（新增）

```text
GET /api/message/conversation?with=<partner_uid>
```

返回当前用户与指定伙伴的全部对话记录（双向），按时间正序排列。同时将对方发来的未读消息标记为已读。

```json
{
  "status": "success",
  "data": {
    "partner_id": 1019,
    "partner_name": "张三",
    "avatar": "/api/user/avatar/1019",
    "messages": [
      {
        "id": 1,
        "sender_id": 1018,
        "content": "你好",
        "created_at": "2026-05-30 12:00",
        "is_mine": true
      }
    ]
  }
}
```

## 5. 前端交互变更

### 5.1 用户名片弹窗

**文件**：`templates/index.html`、`static/js/message.js`

- 标签从 "💌 留言" 改为 "💬 私聊"
- 输入框 placeholder 从 "说句破冰的话吧..." 改为 "发送私聊消息..."
- 组件由 `MessageSender` 重命名为 `ChatManager`
- 发送后**不再隐藏输入框**，清空内容后可继续发送
- 调用方由 `MessageSender.send()` 改为 `ChatManager.send()`

### 5.2 私聊页面（收件箱重写）

**文件**：`templates/panels/inbox.html`

页面改为**双视图结构**：

**会话列表视图**（`#inboxConvList`）：
- 每个卡片显示：对方头像、用户名、最后一条消息预览、时间、未读红点
- 点击卡片进入聊天窗口

**聊天窗口视图**（`#inboxChatView`）：
- 顶部：返回按钮 + 对方用户名
- 中部：消息气泡列表（自己发右对齐琥珀色，对方发左对齐白色），自动滚到底部
- 底部：文本输入框 + 发送按钮，支持 Enter 键发送
- 每 5 秒自动轮询 `/api/message/conversation` 拉取新消息
- 点击"返回"回到会话列表

### 5.3 侧边栏

**文件**：`templates/dashboard.html`

- 菜单项从 "💌 破冰收件箱" 改为 "💬 私聊"

## 7. 数据兼容性

- 迁移过程保留所有历史消息数据。
- 已存在的破冰留言将作为私聊对话的第一条消息出现在会话列表中。
- 不新增数据库表，不改变其他表结构。
- 旧版数据库在应用启动时自动检测并迁移，无需手动操作。

## 8. 验证情况

接口级检查：

- `POST /api/message/send`：同一对用户可连续发送多条消息，不再返回 403。
- `GET /api/message/inbox`：返回按对话伙伴分组的会话列表，含未读数。
- `GET /api/message/conversation?with=<uid>`：返回完整对话记录，双向消息均可见。

页面级检查：

- 用户名片弹窗中可连续发送消息，发送后输入框不清失。
- 私聊页面会话列表正确展示所有对话。
- 点击会话后聊天窗口正常展示历史消息。
- Enter 键发送、返回按钮均正常工作。
